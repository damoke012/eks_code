## Why the PR exists — confirmed correct

QA RisingWave has been down 4h37m. `risingwave-meta-default-0` panics in
`hummock::manager::write_exclusive_cluster_id`:

```
ERROR risingwave_object_store::object: read failed
  called: reqsign::LoadCredential, service: s3, path: hummock/cluster_id/0
  => loading credential to sign http request
  source: request to AWS STS Services failed
```

Meta cannot obtain credentials to read `hummock/cluster_id/0`, so `HummockManager::new` fails and
compute (74 restarts), compactor (74) and frontend (41) all cascade off it. `rw-bootstrap-*` jobs
stuck `Init:0/1` behind meta. **This is genuinely the missing IRSA role — not postgres, not config.**

### 1. (BLOCKER) Missing import blocks

`risingwave-state-op-usxpress-dev` returns 403 (exists) while the QA bucket returns 404 (absent), and
the control bucket also returns 403 — so the probe distinguishes correctly. The module is applied to
dev as well, so the next dev apply hits `BucketAlreadyOwnedByYou` on
`aws_s3_bucket.risingwave_state`.

`risingwave-2-role.tf` documents this exact situation in its header — resources created by AWS CLI
during build-out, adopted via import blocks. This PR copied the resource pattern but not the import
pattern.

Fix: import blocks for the dev bucket (and role, if present), or scope the resource per cluster.

### 2. (BLOCKER) Tim coordination

`risingwave` is Tim's namespace. Mandatory gate, separate from code correctness — same as PR #25.
Not mentioned in the PR description.

### 4. Wiz triage

Dismiss: versioning, replication, MFA delete, object lock, event notifications, logging, default
encryption (SSE-S3 default since 2023), CMK. Wrong for a Hummock state store — RisingWave manages its
own object lifecycle.

Take, as a follow-up covering **both** this file and `risingwave-2-role.tf` (identical gaps):
- bucket policy denying non-TLS (`aws:SecureTransport`)
- lifecycle rule aborting incomplete multipart uploads
