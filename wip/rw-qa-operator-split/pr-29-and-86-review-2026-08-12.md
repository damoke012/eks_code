## PR #29 — `iaac-risingwave-onprem`: move `terraform/` to `deploy/terraform/`

**Branch:** `fix/move-terraform-to-deploy` → `main` · **SHA:** `03b91b4` · 6 files, +0/−0 (pure renames)

### Why it exists

The QA deploy failed at:

```
[STEP] Running Terraform
Error: Cannot find path '.../terraform' because it does not exist.
```

`octo.yaml` has `deploy_scripts_path: deploy`, so only `deploy/` is packaged, but the Terraform sat
at repo root and `deploy.ps1` does `Set-Location terraform`. **The package has never contained the
Terraform** — which is why there is no state in either bucket and why every `dpl` deploy since June
went green without applying anything.

### Assessment

Correct and minimal. Package root is the *contents* of `deploy/`, so `deploy/terraform/` lands at
`terraform/` inside the package and `Set-Location terraform` resolves. Matches `iaac-talos`, whose
Terraform is at `deploy/terraform/`.

### Watch on the first successful apply

`deploy.ps1` writes outputs to `../../outputs/terraform_outputs.yml` — from `terraform/` inside the
package that resolves *above* the work directory. Only runs after a successful apply, so it has
never been exercised. Not a blocker; expect it to be the next thing that fails.

## PR #86 — `iaac-talos-flux-platform`: retarget certificates + virtualservices for op-qa

**Branch:** `feat/risingwave-routes-qa` → **`op-qa`** ✅ · **SHA:** `25de409` · 4 files, +6/−9

Changes `op-dev` → `op-qa` in the dnsNames/hosts of two Certificates and two VirtualServices, and
swaps the external-dns target IPs.

**Base branch is correct** — this repo is branch-per-env, and targeting `op-dev` is how the Argo CD
rollout nearly went wrong in July.

### Concerns

**1. (advisory) A load-bearing comment was deleted.**

```
# Phase 1 cleanup gotcha: external-dns v0.20.0 produces ZERO endpoints
# for istio-virtualservice source when bound Gateway Service is ClusterIP
# without per-VS target annotation. Required.
```

The annotation survives but the reason is gone. Ask for it back in **both** VirtualService files —
someone will otherwise delete the annotation and rediscover this the hard way.

**2. (BLOCKER until verified) The target IPs.**

`10.10.82.21,22,26,27,28,178,180` (dev) → `10.10.82.106,139,23` (QA).

Both clusters live in `10.10.82.0/24` (dev CP `.50`, QA CP `.51`), so a wrong IP here silently
points QA's DNS at **dev's** ingress with no error anywhere. Three IPs matches QA's ingressgateway
NodePool size (3 nodes), which is encouraging but not proof. Verify against live QA.

**3. (BLOCKER until verified) Certificate namespace.**

The diff doesn't show `metadata.namespace`. Gateway is `istio-ingress/shared-http`; for Istio the
TLS secret must be in the **gateway's** namespace. A Certificate in `risingwave` issues fine, routes
nothing, and reports no error — the same silent-failure shape as the Velero Schedule namespace bug
in July.

**4. (gate) Tim coordination** if these land in the `risingwave` namespace.
