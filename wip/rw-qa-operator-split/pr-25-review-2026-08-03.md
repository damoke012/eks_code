### 1. (BLOCKER) Wrong repo for the Flux wiring

PR description says the two Kustomizations go in `iaac-talos-flux-platform`. They don't.

```
grep -rl "risingwave-onprem" ~/work/iaac-talos-flux-platform ~/work/iaac-talos-flux-cluster
→ iaac-talos-flux-cluster/clusters/op-usxpress-qa/flux-system/infra.yaml
→ iaac-talos-flux-cluster/clusters/bm-dev/flux-system/infra.yaml
→ iaac-talos-flux-cluster/clusters/op-usxpress-prod/flux-system/infra.yaml
```

The platform repo mentions RisingWave only in `infrastructure/velero/risingwave-metastore-schedule.yaml`.
PR the wrong repo and the Kustomization never appears — the same "path not found" state that sat
broken on dev for 17 days during the Argo CD fold-in.

### 2. (BLOCKER) `prune: true` + Namespace ownership, in Tim's namespace

`manifests/op-usxpress-qa/operator/kustomization.yaml` includes `namespace.yaml` (kind: Namespace),
and the proposed `risingwave-operator` Kustomization sets `prune: true`. The `risingwave` namespace
already exists on QA (10d), so this **adopts live state into a pruning Kustomization**. If that
Kustomization is deleted, suspended across a path change, or its sourceRef moves, Flux prunes the
Namespace and cascades every object inside it.

Fix: either drop `prune: true` on the operator Kustomization, or move `namespace.yaml` back out of
it (keep it in the workload Kustomization, which is correctly `prune: false`).

### 3. (Advisory) Live dev RBAC ≠ this PR

Root-cause analysis in the PR is correct: the chart's ClusterRoleBindings have fixed names, the
`risingwave-2` release owns them, so the `risingwave`-namespace operator SA had nothing. Verified —
operator was CrashLoopBackOff 133×, `auth can-i list pods` → `no`.

But what is running now is **not** what the PR adds:

```
clusterrolebinding/risingwave-operator subjects:
  ServiceAccount risingwave-operator ns=risingwave-2     ← chart's
  ServiceAccount risingwave-operator ns=risingwave       ← added by hand
meta.helm.sh/release-namespace = risingwave-2
```

None of the PR's three new bindings exist live. So the fix in the cluster is a hand-edit of a
Helm-managed object owned by the RW-2 release — **the next `helm upgrade` of risingwave-2 reverts
it and dev crash-loops again.** After merge: let Flux apply the supplemental bindings, confirm
`auth can-i` still returns yes, then remove the hand-added subject so live matches git.

## Not blocking, but note

- Sequencing in the PR description is right: manifests to `main` first, Kustomization split second.
- Operator Kustomization drops `external-secrets` from `dependsOn` — correct, the chart doesn't need it.
- `healthChecks` on the HelmRelease plus `wait: true` is the right call; `dependsOn` alone only waits
  for the object to apply, not for the chart to install and register CRDs.
- `timeout: 5m` may be tight for a first chart install on a cold node. Watch it; raise if it flaps.
- Verify `kubectl kustomize .../operator` renders the Namespace as `risingwave` — this repo's
  `namespace:` transformer already caused one cross-namespace bug (Velero Schedule, July).
