# op-usxpress-qa has Istio ingress installed and nothing can route through it

**Found 2026-08-20** while looking for somewhere to attach the Argo CD UI (INFRA-1622).
Scope: `op-usxpress-qa`. Dev not yet compared; prod not looked at.

## The state

| | |
|---|---|
| `istio-ingressgateway` DaemonSet | 10/10 Running, 43 days, chart `gateway@1.27.3` |
| Flux `istio-ingress` Kustomization | Ready, `op-qa@sha1:c43d26f` |
| `Gateway` objects, all namespaces | **none** |
| `istio-ingressgateway` Service | **ClusterIP** `10.110.232.146` — ports 80, 443, 4567, 5432, no external IP, no NodePort |

Five VirtualServices exist and reference Gateways that do not:

| Namespace | VirtualService | Gateway referenced | Host |
|---|---|---|---|
| `grafana` | `grafana` | `istio-ingress/shared-http` | `grafana.`**`op-dev`**`.usxpress.io` |

| `istio-ingress` | `rw-sql-passthrough` | `tcp-passthrough` | `rw-sql.`**`op-dev`**`.usxpress.io` |
| `risingwave` | `risingwave-dashboard` | `istio-ingress/shared-http` | `risingwave-dashboard.op-qa.usxpress.io` |
| `risingwave` | `risingwave-overview` | `istio-ingress/shared-http` | `risingwave-overview.op-qa.usxpress.io` |

**So nothing has ever served over Istio on this cluster**, and two faults stack:

1. **No `Gateway` object exists**, so every VirtualService is inert. The two RisingWave ones
   look right because their hostnames *were* adapted to `op-qa` — the adaptation stopped at
   the hostname.
2. **The gateway Service is ClusterIP.** Even with a Gateway, nothing outside the cluster
   could reach it. There is no NodePort and no LoadBalancer address.

That is why everything user-facing on QA today is a separate NodePort service —
`risingwave-frontend-ext`, `risingwave-dashboard-ext`, `risingwave-console-ext`. The Istio
path was built, then bypassed, and nobody noticed the difference because the bypass works.

## Instance seven of the copied-identifier class

`grafana` on **QA** routes `grafana.op-dev.usxpress.io`, and both TCP passthrough
VirtualServices carry `op-dev` hostnames. `scripts/check-foreign-cluster-ids.sh` flags all
three on sight — see [[manifests-copied-across-branches]].

## What this blocks

* **INFRA-1622** — Argo CD UI. `argocd-server` is ClusterIP with `server.insecure: true`, so
  it expects TLS to terminate at a gateway that does not exist.
* **INFRA-1639** — Argo CD SSO for app teams. Blocked *behind* 1622, not beside it: there is
  no point authenticating to something unreachable.
* **INFRA-1645** — the RisingWave L4 routes. Same root cause, not a separate defect.
* Grafana and both RisingWave UIs, which are presumed working and are not.

## Proven

* Ingress **workload** healthy and Flux-managed for 43 days, 2026-08-20.
* Zero `Gateway` objects on the cluster, 2026-08-20.
* Gateway Service is ClusterIP with no external entry point, 2026-08-20.

## Tested and killed

* **A NodePort for `argocd-server`** — rejected 2026-08-20. It would match what QA does today
  and unblock 1639 this week, but it adds a sixth thing bypassing the ingress that was already
  built, and leaves four other routes dead. Fixing the gateway serves all of them at once.

## Traps

1. **A VirtualService binding to a non-existent Gateway reports nothing.** No error, no
   status condition, no event. It simply never serves. Verify a route by requesting it, not by
   listing the object — the same shape as `SecretSynced` and `Synced Healthy`.
2. **An ingress gateway Service can be healthy and unreachable.** ClusterIP with ten running
   pods looks exactly like a working ingress in `get pods`.
