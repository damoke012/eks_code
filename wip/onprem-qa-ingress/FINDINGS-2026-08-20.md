# op-usxpress-qa ingress — what actually serves, and what does not

> ### ⚠️ Corrected 2026-08-20, same day
> The first version of this note claimed **"nothing can route through it"**. That was wrong,
> and wrong twice over:
> * `kubectl get gateway -A` returned "No resources found" because it resolved to
>   `gateways.gateway.networking.k8s.io` (Gateway API), not `gateways.networking.istio.io`.
>   Asking for the right kind shows `istio-ingress/shared-http`, 43 days old.
> * "Service is ClusterIP therefore unreachable" ignored `hostNetwork: true`, injected into
>   the DaemonSet by a Flux postRenderer in `release.yaml` — the gateway pods bind node ports
>   directly, so the Service type says nothing about reachability.
>
> The test that settled it took five seconds and should have come first:
> `curl https://risingwave-dashboard.op-qa.usxpress.io/` → **200**.
>
> Left in place rather than deleted, because the reasoning that produced it is the same
> "listed the object instead of requesting the thing" habit the note itself warns about.

**Three of the five serve; two cannot, for two different reasons:**

| VirtualService | Serves? | Why |
|---|---|---|
| `risingwave-dashboard`, `risingwave-overview` | ✅ | host matches the `*.op-qa.usxpress.io` wildcard, gateway exists |
| `grafana` | ❌ | routes `grafana.`**`op-dev`**`.usxpress.io` — a dev hostname, so it never matches QA's wildcard |
| `rw-sql-passthrough`, `rw-postgres-passthrough` | ❌ | bind to `tcp-passthrough`, and **`gateway-tcp-passthrough.yaml` exists on the `op-dev` branch and was never ported to `op-qa`** |

The second row is the inverse of the usual copy defect: not a stale value, a **missing file**.
`git ls-tree origin/op-dev` lists `infrastructure/istio-ingress/gateway-tcp-passthrough.yaml`;
`origin/op-qa` does not have it. That is INFRA-1645's root cause.

The NodePort services (`risingwave-frontend-ext`, `-dashboard-ext`, `-console-ext`) sit
alongside the working ingress rather than compensating for it.

## Instance seven of the copied-identifier class

`grafana` on **QA** routes `grafana.op-dev.usxpress.io`, and both TCP passthrough
VirtualServices carry `op-dev` hostnames. `scripts/check-foreign-cluster-ids.sh` flags all
three on sight — see [[manifests-copied-across-branches]].

## What this blocks

* **INFRA-1622** — Argo CD UI. Needs **one VirtualService**; the gateway it would bind to is
  already there and already terminating TLS with the wildcard certificate, which is exactly
  what `server.insecure: true` expects.
* **INFRA-1639** — Argo CD SSO for app teams. Blocked *behind* 1622, not beside it: there is
  no point authenticating to something unreachable.
* **INFRA-1645** — the RisingWave L4 routes. Same root cause, not a separate defect.
* Grafana and both RisingWave UIs, which are presumed working and are not.

## Traps

1. **A VirtualService binding to a non-existent Gateway reports nothing.** No error, no
   status condition, no event. It simply never serves. Verify a route by requesting it, not by
   listing the object — the same shape as `SecretSynced` and `Synced Healthy`.
2. **`kubectl get gateway` is ambiguous.** It can resolve to `gateway.networking.k8s.io`
   instead of `networking.istio.io` and answer "No resources found" about a kind you were not
   asking about. Always `kubectl get gateways.networking.istio.io`.
3. **Service type does not tell you reachability.** This gateway is ClusterIP and reachable,
   because `hostNetwork: true` is injected by a Flux postRenderer in `release.yaml` — invisible
   in both the Service and the chart values.
4. **Curl first.** Both mistakes above cost more time than the request that settled them.
