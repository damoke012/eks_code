## Instance seven of the copied-identifier class

## What this blocks

* **INFRA-1622** — Argo CD UI. Needs **one VirtualService**; the gateway it would bind to is
  already there and already terminating TLS with the wildcard certificate, which is exactly
  what `server.insecure: true` expects.
* **INFRA-1639** — Argo CD SSO for app teams. Blocked *behind* 1622, not beside it: there is
  no point authenticating to something unreachable.
* **INFRA-1645** — the RisingWave L4 routes. Same root cause, not a separate defect.
* Grafana and both RisingWave UIs, which are presumed working and are not.

## The Argo CD route, and the hour it cost after it already worked — added 19:40Z

`argocd.op-qa.usxpress.io` serves the Argo CD UI. Getting there took four rounds, and only
the first was a real defect:

| Round | What reported success | What was actually wrong |
|---|---|---|
| 1 | PR #98 merged | `git commit -am` never staged the new file; the kustomization referenced a file that did not exist and Flux went `BuildFailed` |
| 2 | PR #99 merged, Flux `Ready` | the VirtualService had no `external-dns` target annotation — spec copied, `metadata` left behind |
| 3 | external-dns logged `Desired change: CREATE` | nothing; the record was created correctly |
| 4 | — | **this workstation's DNS cache**, holding a negative answer from rounds 1–3 |

Round 4 is the one worth remembering. `dig +short argocd.op-qa.usxpress.io` was empty and
`curl` returned `000` for roughly an hour **after the record existed and the route served**.
The authoritative nameserver had it the whole time. WSL forwards DNS to the Windows host
resolver, which caches negative answers on its own schedule; nothing in Linux clears it.

`scripts/check-onprem-route.sh <host> --context <ctx>` now settles this in one run: it queries
the authoritative nameserver **separately** from the local resolver, curls by `--resolve`
against each target address so `000` cannot hide whether routing works, and diffs against
another route on the same gateway. On 2026-08-20 it returned authoritative
`10.10.82.23 10.10.82.106 10.10.82.139` and `200` from all three, while the plain curl was
still `000`.

## Traps

1. **A VirtualService binding to a non-existent Gateway reports nothing.** No error, no
   status condition, no event. It simply never serves. Verify a route by requesting it, not by
   listing the object — the same shape as `SecretSynced` and `Synced Healthy`.
2. **`kubectl get gateway` is ambiguous.** It can resolve to `gateway.networking.k8s.io`
   instead of `networking.istio.io` and answer "No resources found" about a kind you were not
   asking about. Always `kubectl get gateways.networking.istio.io`.
3. **Service type does not tell you reachability.** This gateway is ClusterIP and reachable,
   because `hostNetwork: true` is injected by a Flux postRenderer in `release.yaml` — invisible
   in both the Service and the chart values.
4. **Curl first.** Both mistakes above cost more time than the request that settled them.
5. **A negative DNS answer outlives the defect that caused it.** Once you have queried a name
   that does not exist, your resolver will keep saying so after it does exist — and on WSL the
   cache that matters is the Windows one. Query the authoritative nameserver directly
   (`dig @$(dig +short NS usxpress.io | head -1) <host>`) before believing DNS is broken.
6. **`curl` `000` is two failures wearing one code** — did not resolve, and resolved but did
   not connect. `--resolve <host>:443:<ip>` separates them in one command.
7. **external-dns `Desired change: CREATE` is an intention, not a receipt.** It is logged
   before `ChangeResourceRecordSets` returns. Confirm against the zone, not against the log.

## The L4 plane, settled 20:05Z

* `rw-sql.op-qa.usxpress.io:4567` — **serves**. TLS handshake from all three gateway addresses,
  `CN = rw-sql.op-qa.usxpress.io`. INFRA-1645 done.
* `rw-postgres.op-qa.usxpress.io:5432` — resolves, routes, and serves nothing.
  `ghostunnel-rw-postgres` runs `--listen=:4567` behind a Service that is `5432 -> 5432`.
  `manifests/op-usxpress-dev/ghostunnel-rw-postgres.yaml:93` is identical, so **op-dev has
  never served this endpoint** since Phase 1 closed 2026-06-01. Repo is
  `variant-inc/iaac-risingwave-onprem`, not platform. Filed separately.
* Correction to the "What this blocks" list above: INFRA-1645 was described there as the same
  root cause as the missing Gateway. Half right — the Gateway was missing *and* both routes
  were dev copies *and* the postgres backend listens on the wrong port. Three defects stacked,
  each of which alone produces "resolves but does not serve".
