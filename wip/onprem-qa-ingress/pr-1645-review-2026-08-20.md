## Outcome — merged as PR #102, verified 2026-08-20 20:05Z

`rw-sql.op-qa.usxpress.io` is green end to end: Gateway exists, sniHosts matches, backend has
two endpoints, DNS authoritative and local agree on `.23 .106 .139`, and all three addresses
complete a TLS handshake presenting `CN = rw-sql.op-qa.usxpress.io`.

**The ordering argument held.** After QA processed the new desired state, both dev names still
return dev's seven workers. QA never adopted them, so it never deleted them.

`rw-postgres.op-qa.usxpress.io` fails at the handshake only — and the cause is outside this
PR's scope. `ghostunnel-rw-postgres` is started with `--listen=:4567` while its Service is
`5432 -> targetPort 5432`, so nothing listens where traffic arrives. Same in
`manifests/op-usxpress-dev/`, so dev has never served this endpoint either, since 2026-06-01.
Filed separately (`scripts/file-ghostunnel-listen-port.py`); INFRA-1645 is not reopened.

## Tested and killed

* **Porting the Gateway on its own, as the ticket literally asks.** Rejected: it activates two
  VirtualServices still carrying dev hostnames, so QA's external-dns adopts them, and the
  subsequent rename deletes dev's live records. The ticket's stated scope is not safe on its own.

## Traps

1. **A missing Gateway costs the route AND the DNS record.** external-dns skips a
   VirtualService whose gateway will not resolve, so no record is ever created — and no error
   appears on either object. Same family as `SecretSynced` and `Synced Healthy`.
2. **A correct destination hides a wrong hostname.** These routes pointed at the right QA
   Services the whole time; only the advertised name and target were foreign, which is
   invisible from inside the cluster.
3. **`--policy=sync` on a zone-wide filter makes hostname renames destructive.** What a
   cluster stops wanting, it deletes. Ordering is a correctness property, not a preference.
4. **Absence of an owner label is not absence of an owner.** Ownership of `risingwave` on
   op-qa lives in INFRA-1624, not in `metadata.labels`. Checking the cluster and concluding
   "unowned" is the same error as an empty grep proving absence — verify where the fact is
   actually recorded before concluding it isn't there.
5. **A readiness probe on a status port is not evidence about a data port.** Both ghostunnel
   pods report `READY true, 0 restarts` while one of them serves nothing, because the probe is
   `tcpSocket: {port: status}` — ghostunnel's 9090 listener. Tenth instance today of a green
   signal about an adjacent step. Probe the port that carries the traffic.
6. **An ownership rule without a cluster attached reads as a contradiction.** `pr-review-rw`
   and the `risingwave-onprem` memory disagreed only because both describe op-dev and neither
   said so. Nothing was stale. Scope every ownership claim to a cluster.
