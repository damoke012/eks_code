# Prod deploy 0.5.6 failed: 403 on the Terraform state backend

**Date:** 2026-09-01  **Ticket:** INFRA-1674  **Release:** 0.5.6 (channel `release`, package 0.5.5)

## What happened

`octopus release deploy --version 0.5.6 --environment production` ran on worker
`octopusworker-1.prod.usxpress.io` (pool `usxpress-production`) and failed in 16 seconds:

```
terraform init -backend-config=bucket=lazy-tf-state-425rbol87rmn6c7m \
  -backend-config=key=iaac/risingwave/op-usxpress-prod.tfstate ...
Successfully configured the backend "s3"!
Error: Error refreshing state: Unable to access object
  "iaac/risingwave/op-usxpress-prod.tfstate" in S3 bucket
  "lazy-tf-state-425rbol87rmn6c7m": StatusCode: 403 ... Forbidden
```

`init` succeeded — configuring an S3 backend does not touch the bucket. The first
read did.

## Cause

`lazy-tf-state-425rbol87rmn6c7m` is the **QA** account's state bucket (527101283767).
The production worker runs with prod-account (937464026810) credentials and cannot read
it. Prod's bucket is `lazy-tf-state-ipp58n854uhpw13x`.

The value came from `scripts/setup-octopus-rw-prod.py`, where `S3_BUCKET` was copied
verbatim out of the QA script `wip/qa-cluster-standup/octopus-qa-env-setup/setup-octopus-rw.py`
and never re-derived for prod. It was written into production scope on 2026-08-31 and
**reported as verified**.

## Why both guards passed

Two checks were green over a wrong value, for the same reason.

1. **The foreign-literal gate matched account IDs, not buckets.** `FOREIGN` listed
   `527101283767`, but the QA bucket is named `lazy-tf-state-425rbol87rmn6c7m` — the
   account it belongs to appears nowhere in its name. A name resolves to an account;
   the gate only read the name.
2. **The read-back checked presence, not value.** It confirmed the ten names were
   production-scoped and printed "Verified". It never compared a single value to what
   the script declared, so a wrong value was indistinguishable from a right one.

Both are the same defect as [[proxy-is-not-the-property]]: measuring something adjacent
to the property that matters. This is instance 5, and the first where the proxy was in a
check I wrote to prevent exactly this class.

## Fix

`scripts/setup-octopus-rw-prod.py`:

- `S3_BUCKET` = `lazy-tf-state-ipp58n854uhpw13x`, with the provenance in a comment
  (`wip/prod-standup/add-prod-vars.py` `TF_VAR_tf_state_bucket` — what the prod
  *cluster* build used against the same worker pool).
- `FOREIGN` now carries the other environments' **bucket names** as literals, since
  the account IDs never appear in them.
- New `--fix` mode: a name already production-scoped whose value differs is corrected
  in place. Without `--fix` the script now **aborts on drift** rather than printing
  `skip (already production-scoped)` and exiting 0 — the old behaviour meant a wrong
  value could never be repaired by re-running.
- Read-back compares **values** for all ten and exits non-zero on any mismatch.

## Proven

- Deploying to `production` reaches the worker, extracts the package, runs the script,
  and gets as far as Terraform — the release/channel/lifecycle/worker-pool chain is
  sound. Everything preflight claimed about it held.
- `TfApply` is not production-scoped: this run was plan-only and nothing was created.
- The state key `iaac/risingwave/op-usxpress-prod.tfstate` has never existed. Prod
  RisingWave state is greenfield.

## Tested and killed

- **"It is a permissions gap on the prod role."** Not the first cause. The bucket is in
  another account; no prod-side grant would fix it. Whether the prod role also needs
  `s3:ListBucket` is untested and still open — see traps.

## Traps

- **A 403 on HeadObject does not mean the object exists and is denied.** S3 answers 403
  rather than 404 for a missing key when the caller lacks `s3:ListBucket` on the bucket.
  After the bucket is corrected, a *second* 403 would mean the prod role is missing
  `s3:ListBucket` on `lazy-tf-state-ipp58n854uhpw13x` — a different fix, not a repeat.
  Do not read the two as the same failure.
- `terraform init` printing "Successfully configured the backend" says nothing about
  access. The backend is validated on first state read.
- The remaining nine production-scoped variables were written by the same copy-from-QA
  pass. `--fix` (dry run) re-checks all ten against the declared map; run it before
  redeploying rather than assuming only the bucket was wrong.
