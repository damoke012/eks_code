# RisingWave ETL — promotion readiness and a credential exposure

**Cluster:** `op-usxpress-dev` (10.10.82.50) · namespace `risingwave` · RisingWave v2.8.2
**Read on:** 2026-08-18, read-only queries against `rw_catalog` from the running `postgres-postgresql-0` pod
**For:** Tim, Idris · **From:** Doke (on-prem platform)

Context: we're designing how application workloads get promoted on-prem — build in dev, push an
image to ECR, deploy to QA and prod through Argo CD. I went looking at how the RisingWave ETL is
built to see whether it fits that model. Two things came out of it: something that needs fixing
now, and a small change that would make the pipeline promotable.

---

## 1. Credentials are readable in the catalog — needs rotating

`brand_source_kafka` carries its Confluent Cloud credentials as literals in the source definition:

```
properties.sasl.username          = '<REDACTED — live Confluent API key>'
properties.sasl.password          = '<REDACTED — live Confluent API secret>'
schema.registry.username          = '<REDACTED>'
schema.registry.password          = '<REDACTED>'
```

They are stored as `"type": "plaintext"` in `rw_catalog.rw_sources.connector_props`, so **any
principal that can read the catalog can retrieve working Confluent Cloud credentials** — `root`,
`rwadmin`, `postgres`, and anything else granted catalog read. No cluster-admin access needed; a
SQL connection is enough.

They were visible in a terminal session on 2026-08-18 while we were reading the catalog, so please
treat them as exposed and rotate rather than assuming limited blast radius.

**This is a fix worth making on its own merits, independent of anything below.**

## 2. The secret layer already exists and isn't being used

Fifteen secrets are already defined in this database — someone built this properly:

```
kafka_bootstrap_server            kafka_security_protocol       kafka_sasl_mechanism
kafka_api_key                     kafka_api_secret              kafka_service_account
kafka_resource_id                 kafka_rest_endpoint           kafka_group_id_prefix
kafka_schema_registry_endpoint    kafka_schema_registry_api_key
kafka_schema_registry_api_secret
mongodb_connection_string         mongodb_username              mongodb_password
```

Fourteen of the values the source DDL inlines have a secret sitting ready for them. Only the topic
name has no home yet.

## 3. What the ETL looks like today

```
Confluent Cloud (CDC, Avro, schema registry)
  topic  dev_brand_management_cdc_brand_avro
        │
        ▼
  brand_source_kafka        append-only; INCLUDE partition / offset / timestamp
        │
        ├─►  brand_mv_raw     SELECT *
        ├─►  brand_mv_state   MAX(kafka_offset) GROUP BY "companyLink", kafka_partition
        └─►  brand_mv_flat    raw ⨝ state ON last_offset  → newest row per companyLink,
                              columns renamed (CMCMNM → company_name, CMADD1 → address1, …)
        │
        ▼
      sinks: none yet
```

Four streaming jobs, all `CREATED`, ADAPTIVE parallelism. `rw_sinks` is empty — the pipeline
ingests and transforms but doesn't yet write anywhere. The MongoDB secrets suggest a Mongo sink is
the intended next step.

## 4. Why this currently can't be promoted

Everything that varies by environment is a literal inside the DDL:

| Value in the DDL | Varies per environment? |
|---|---|
| `topic = 'dev_brand_management_cdc_brand_avro'` | yes — `dev_` prefix |
| `group.id.prefix = 'dx__dev_risingwave_risingwave_dev'` | yes |
| `properties.bootstrap.server` | likely |
| sasl + schema-registry credentials | yes — and see §1 |

The promotion model we're building is **build once, promote the same artefact**: the image is built
in dev, pushed to ECR by digest, and the *same digest* is deployed to QA and then prod, with each
cluster supplying its own configuration at runtime. Nothing is rebuilt per environment — what runs
in prod is byte-identical to what was tested in dev.

With the values inlined, an artefact built in dev would carry dev's topic and dev's credentials into
QA. So the SQL has to become environment-agnostic first. This is a precondition, not a preference.

## 5. The change

Reference the secrets that already exist:

```sql
CREATE SOURCE brand_source_kafka ( ...columns unchanged... )
INCLUDE partition AS kafka_partition
INCLUDE offset    AS kafka_offset
INCLUDE timestamp AS kafka_timestamp
WITH (
  connector                    = 'kafka',
  topic                        = SECRET kafka_topic_brand,          -- new
  properties.bootstrap.server  = SECRET kafka_bootstrap_server,
  properties.security.protocol = SECRET kafka_security_protocol,
  properties.sasl.mechanism    = SECRET kafka_sasl_mechanism,
  properties.sasl.username     = SECRET kafka_api_key,
  properties.sasl.password     = SECRET kafka_api_secret,
  group.id.prefix              = SECRET kafka_group_id_prefix,
  scan.startup.mode            = 'earliest'
)
FORMAT PLAIN ENCODE AVRO (
  message                  = 'message_name',
  schema.registry          = SECRET kafka_schema_registry_endpoint,
  schema.registry.username = SECRET kafka_schema_registry_api_key,
  schema.registry.password = SECRET kafka_schema_registry_api_secret
);
```

One new secret (`kafka_topic_brand`, or a prefix secret if you'd rather compose it). Everything else
already exists. The MVs need no change — they only reference the source by name.

Note this is a `CREATE SOURCE` change, so it means dropping and recreating the source and the three
dependent MVs. Worth sequencing deliberately rather than doing it live; `scan.startup.mode =
'earliest'` means the rebuild re-reads the topic from the start.

## 6. Who owns what

| | Owner |
|---|---|
| The **value** of a Confluent API key / topic name | whoever provisions the Confluent service account — not platform |
| **Getting it into each cluster** | platform: AWS Secrets Manager → External Secrets → RisingWave secret |
| **The SQL** | the RisingWave team, and it should contain no environment-specific value at all |

Platform shouldn't be the source of truth for a credential it doesn't issue — but it should be the
only path by which one reaches a cluster. That's the same mechanism already carrying every other
secret on these clusters, so there's nothing new to build; QA and prod would get their own values
under their own Secrets Manager paths.

## 7. Where this leads

Once the DDL is environment-agnostic:

```
dev    developer commits SQL  →  GitHub Actions on the in-cluster runner
                              →  build image (SQL + psql + apply script)
                              →  push to ECR by digest
                              →  apply against RisingWave in dev  (the test)

QA     PR bumps the QA overlay to that digest
       Argo CD Application in `app-risingwave` runs it against QA's RisingWave
       RW team watch the sync and the job logs in the Argo UI

prod   same digest, prod overlay, PR is the gate
```

Two things this gives the RisingWave team specifically: your pipeline deployments become visible to
you in Argo CD, separate from the RisingWave platform itself (which stays in Flux and isn't yours to
worry about); and what runs in prod is provably the thing that passed in dev.

One dependency on our side: the apply job must be safely re-runnable, since Argo CD will re-sync it.
That's the tracking-table work already filed as INFRA-1491.

## 8. Suggested order

1. **Rotate the Confluent credentials** (§1) — independent of everything else
2. **Refactor the source DDL onto the existing secrets** (§5) — closes the exposure permanently and
   is the precondition for promotion
3. **Add `kafka_topic_brand`** and get QA/prod values into Secrets Manager so ESO can deliver them
4. **Then** we wire the image build and the Argo CD Application — platform side, our work

Steps 1–3 are worth doing whether or not we ever containerise this.
