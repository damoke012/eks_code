Prod Readiness Plan

The ask: sign in to the production cluster with AWS single sign-on, and close whatever else stops production being genuinely production-ready.

The good news: QA already has all of this, and we wrote down what went wrong doing it. This is a difference against QA, not a design.

Single sign-on: seven pieces, two of them new

QA went live on 28 July. Afterwards, signing in there produced the right identity and the right groups with no certificate involved at all. The same seven pieces apply to production; five are copies, two carry production's own values.

The split follows the repository boundary. Everything held in Git was copied to production's branch and applied. The one piece held in Terraform was switched on for QA only, by a setting that was never extended to production.

This shrinks the risky step rather than removing it. The hazard was that the API server will not start if a file is missing — and the component that writes that file has been running on production for some time. The prerequisite is already satisfied. Confirm the file on each control-plane machine anyway, then make the change.
The production sign-on role already exists. Its identifier carries a real generated suffix, which cannot be invented — so the permission set was created. Who is assigned to it is unknown.

A defect found by the same check — and it affects QA too.

Four of the six role mappings across the two clusters name a role that cannot exist, because the identifier still contains placeholder text where a value belongs. Only the administrator tier works, on either cluster. Someone in the operator or reader tier would sign in successfully and arrive with no permissions at all — which reads as "sign-on is broken" and is really an unfinished entry. It has been this way for months, unnoticed, because only administrators have used it. One line of checking would have caught it.

And it cannot be fixed by filling in a value. Listing the sign-on roles in both accounts found no operator or reader permission set in either one — so those two tiers need the permission sets created and assigned in Identity Center first. That is console work and its own ticket, not a text substitution.
QA also carries a second administrator role it does not recognise. The newer naming exists in the QA account, but QA maps only the original name. Anyone granted the newer one on QA signs in and lands with no permissions. QA looks mid-rename, and the map was never finished.
Production's administrator mapping is exact. The identifier in the cluster matches a role that exists, suffix and all. Production administrator sign-in will work the moment the API server setting is on — with no AWS work at all.

The one step that can take production down

The API server will not start if a file it is told to read does not exist.

Piece 5 points the API server at a file. Piece 1 is what writes that file — on every control-plane machine. Land them in the wrong order and the production control plane does not come back.

So the order is not a preference

  1. Land the authenticator. Confirm the file exists on all three control-plane machines.
  2. Only then land the API server setting, and watch the control plane restart one machine at a time.
  3. Keep the break-glass certificate access open in another window throughout.

The reason that third step saves you: the setting needs the file, not a running service. If the authenticator itself fails, single sign-on stops working and certificate access still works. That escape hatch only helps if someone is already holding it.

This needs a change window. It is the only item in this plan that touches a production control plane.

Three traps QA already paid for

Production applies for real. Everywhere else, an Octopus deployment prints its plan and changes nothing unless a flag is set — and that flag is on for production. The usual "deploy it to see the plan" is not safe here.
The settings file in Git is not what a deployment reads. On QA the enabling value sat in a Git file and was never read; the deployment takes its values from Octopus. Piece 6 is an Octopus variable, and putting it in Git instead looks right and does nothing.
A release freezes its variables when it is created. Adding the variable does not reach a release that already exists. Refresh it, or deploy a new one — otherwise the deployment is another silent success.

The order of work

Measure first — nothing below changes anything

KP=$HOME/.kube/op-usxpress-prod.yaml
kubectl --kubeconfig=$KP get --raw /version | head -c 200; echo
kubectl --kubeconfig=$KP get nodes -o wide --no-headers | awk '{print $1"  "$5"  "$8}'
kubectl --kubeconfig=$KP -n kube-system get ds,deploy -o name | grep -i auth || echo "NO authenticator on prod"
kubectl --kubeconfig=$KP get certificate -A -o custom-columns=NS:.metadata.namespace,N:.metadata.name,READY:.status.conditions[0].status,EXPIRES:.status.notAfter
kubectl --kubeconfig=$KP get externalsecrets -A -o custom-columns=NS:.metadata.namespace,N:.metadata.name,READY:.status.conditions[0].status | head -20

These settle the Kubernetes and operating system versions, whether an authenticator already exists, whether any certificate is expiring behind a healthy status, and whether secret delivery is working. Production is not missing anything. Measured on 20 October, it returns the same pod count as QA in 19 of 20 namespaces, the same 13-machine layout and the same version — the only difference is the one application, 14 pods against 13. So readiness is not a question of absent components. What remains is configuration and behaviour: whether alerts are routed, whether a role can write, how people sign in, and what version is running.
One hint worth chasing before sizing the sign-on work. The core namespace holds 32 pods on both clusters, and QA's sign-on component lives there. If production's count already includes it, most of this work may already be done and only the API server setting, the role mapping and the permission set remain. Equal counts are a hint, never a finding — check it directly.

One item may outrank this entire list.

QA and production both run a Kubernetes version whose support ended in February, and it is the first release of that line — thirteen patches shipped afterwards and none was applied. It cannot be a task inside this sprint, because it is control-plane work across three clusters with no written procedure. But a cluster eight months past end of life is a harder answer to "is it production-ready" than anything else on this page. Raise it as its own piece of work before this sprint's scope is agreed.

Split the sign-on work into two tickets. The Git half is low risk and can land any time; the control-plane half needs a window and a second person. One ticket for both would stall the safe half behind the scheduling of the risky one.
