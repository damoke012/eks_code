On-Prem Platform Reference

Three self-managed Talos Linux Kubernetes clusters in the datacenter, built by Terraform through Octopus, configured entirely by Flux from Git, running applications through Argo CD, and joined to AWS by a VPN and transit gateway that already carries traffic.

How a cluster is built

The cluster's whole specification lives in a web form. 121 Terraform variables on the Octopus project — addresses, cluster names, vSphere placement, node sizes — in no repository and under no review. The repository that manages Octopus itself creates environments, worker pools and lifecycles, and no project variables at all.
A green deployment may have applied nothing. The apply step is behind a flag that is off by default: the deploy prints the full plan, skips the apply and reports Success. Confirm the task log contains Apply complete!. QA has had it on since July, so QA deploys are live.
A variable scoped to "all environments" is invisible to anything that copies an environment's explicit settings. A generator built that way once planned 13 machines for a 4-machine cluster.
A release freezes its variables when it is created. Correcting a variable afterwards does nothing to a release that already exists.
An environment missing from a lifecycle can never receive a deployment — and adding it to the environment list alone gives a green pull request and a dead environment.

Seven vSphere placement values exist only in Octopus — datacenter, datastore, cluster, folder, network, content library and image. A new environment cannot be built without them, and they are in no repository.

Three corrections to what this page assumed. The network layer is Cilium. Istio runs in ambient mode, so workloads are meshed without a helper container each. And KEDA is installed — it appeared in none of our notes.
Rook-Ceph is genuinely live, not merely stood up once — it is the largest thing running on the cluster. The sign-on component is already managed from Git on QA, and has been for 83 days, which is what makes it a clean copy for another cluster rather than a rebuild.
Production returns the same counts in 19 of 20 namespaces — the only difference is RisingWave, 14 pods against 13. So production is not missing platform components; its readiness gaps are configuration and behaviour, not presence. dev is the only cluster not measured.
Flux versions differ between clusters — dev runs a newer release than QA and production. So "prove it on dev first" does not hold for anything that depends on Flux's own behaviour: dev is ahead, not representative.

DNS is ours and automatic. external-dns reads the annotations on a route definition and writes the record into Route 53. The zone lives in the network account, 155768531003, and each cluster has its own owner identifier so one cluster cannot overwrite another's records. Each record points at that cluster's own worker addresses — dev 7, QA 3, production 10.

A copied route definition fails silently. It carries the source cluster's hostname or targets, external-dns does exactly what it is told, and nothing reports a problem.
Looking a name up to see whether it exists is what hides it. The zone caches a negative answer for 24 hours. Ask the Route 53 API; only resolve names already confirmed to exist.

Corporate DNS and Active Directory are reachable from inside the cluster — the cluster's resolver forwards the corporate domain, and secure LDAP is open.

The link to AWS — traced in full on 20 October

This is the part most people assume is missing. It is not.

Read a transit gateway's route table by the attachment's association, never by position. Asking for "the first" route table can return one the network in question does not use. On 20 October every table happened to agree, so the shortcut gave the right answer for the wrong reason.

Egress to the public internet works, and the public certificate bundle is trusted — proven from a pod: two external partner endpoints answered with a valid certificate chain and no extra configuration.

Secrets and the container registry

External Secrets Operator pulls from AWS Secrets Manager into Kubernetes, per cluster, from that cluster's own AWS account. The value never appears in a repository.

A green sync is not a valid value. On an error the operator still writes the keys it could resolve, and the pod then dies at container creation with zero restarts — invisible to every restart alert. Count the keys and check none is empty.
A secret reference resolves when the pod is created. A container restart replays the old value, so a rotated secret can take months to actually arrive.
The platform's own AWS role could not write its own secrets — it held a single permission. QA was fixed in August; dev and production are still open.

Registry access is refreshed by a job that writes a pull secret into every namespace every five minutes and attaches it to every service account. So a pull secret's creation date is not the age of its contents — a seven-week-old secret can hold a fresh token.

The registry itself is shared across the organisation, and its repositories grant pull and push to any account in it. The on-prem defence is pinning images by digest, enforced by policy, rather than trusting a version label.

The group membership claim never arrives; application roles do. Permissions must be written against role values. A sign-in that succeeds and lands on an empty screen is an authorisation problem, not a broken login.
One Entra registration is shared by all three environments — only the redirect address differs. A new environment is an address added to the existing registration, and its secret is a copy, not a new identity.
Identity names do not cross systems. The name used inside Kubernetes is not a directory group, and Argo CD uses a different one again. Three names, three systems, no automatic relationship.

What is not measured, and how to settle it

Read-only, from a machine with cluster access.

KQ=$HOME/.kube/op-usxpress-qa-sso.yaml
kubectl --kubeconfig=$KQ get --raw /version | head -c 200; echo
kubectl --kubeconfig=$KQ get nodes -o wide --no-headers | awk '{print $1"  "$5"  "$8}'
kubectl --kubeconfig=$KQ get pods -A --no-headers | awk '{print $1}' | sort | uniq -c | sort -rn
kubectl --kubeconfig=$KQ get kustomizations -A --no-headers | head -30

The first gives the Kubernetes version and each machine's operating system image, which is the Talos version. The second lists every namespace with a pod count, settling what is actually installed. The third names each platform component and whether it is healthy.

Still unverified: dev is the only cluster not measured. Also open: whether production's alerting was ever completed, whether the dev and production permission fixes were applied, and whether any certificate is expired behind a healthy status on any cluster.

The finding that outranks everything else on this page.

QA and production both run Kubernetes v1.32.0 — the first release of a line whose support ended on 28 February 2026, and whose final patch was 1.32.13. Both clusters are eight months past end of life and have never taken a patch within their own version. Because these clusters are self-managed, no vendor extended support applies; the managed cloud clusters run 1.35 and 1.36. Upgrading is control-plane work across three clusters with no written procedure, so it is a piece of work in its own right rather than a task inside something else.
