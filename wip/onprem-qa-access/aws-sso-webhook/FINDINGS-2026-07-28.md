# AWS SSO cluster access on op-usxpress-qa — what actually bit us

**Outcome: WORKING.** `kubectl auth whoami` → `sso:doke@usxpress.com`, groups
`[onprem-platform-admins system:authenticated]`, via SSO only — no cert, no key. Authenticator 3/3 Running,
0 restarts, Flux-managed. Idris is assigned the permission set and needs only the client setup.

The design was right first time. Everything below is delivery, and most of it is not specific to this work.

---

## 1. Octopus reports Success while applying nothing — `TfApply = false`

**Five consecutive QA deploys "succeeded" in ~1 minute each and changed nothing.**

```
TfApply = false   ['(all)']       <- QA and dev inherit this
TfApply = true    ['production']
```

The step runs `terraform plan`, prints `Plan: 0 to add, 3 to change, 0 to destroy`, **skips the apply**, and
exits 0. The task goes green.

This is the most dangerous thing found today and it has nothing to do with SSO: **anyone changing QA
infrastructure through Octopus right now would reasonably believe it took effect.** The plan is even printed
in the log, which makes it *more* convincing, not less.

- Fixed for this work by adding `TfApply = true` scoped to `qa`.
- ⚠️ **Decide deliberately whether QA should stay apply-enabled.** If the global `false` was a safety catch
  added during prod standup, leaving qa `true` makes every future QA deploy live.
- **Worth a ticket:** the step should log `PLAN ONLY — TfApply=false` loudly, or exit non-zero when a plan is
  non-empty and apply is disabled. Silence plus a green tick is the problem.

## 2. Git tfvars are NOT what deploys read

`enable_aws_iam_authenticator = true` in `deploy/terraform/envs/qa.tfvars` was never read. Octopus injects
`TF_VAR_*` as `env.auto.tfvars`; `-var-file` is not used. Documented already in
`wip/qa-cluster-standup/APPLY-irsa-grafana.md:50` — and still cost an hour.

Two independent sources of the same value, one of which looks authoritative in git and isn't. This is the
INFRA-1589 drift class in its purest form. `add-octopus-var.py` (this dir) writes the Octopus side.

## 3. A release pins a variable SNAPSHOT

Adding a project variable does **not** reach an existing release. Requires **Update Variables** on the
release page, or a new release. Deploying in between is another silent no-op.

## 4. The AWS profile's ROLE is what's mapped, not the user

`aws-auth` maps `AWSReservedSSO_op-qa-platform-admin_<hash>`. The existing `usx-qa` profile assumes
`AWSAdministratorAccess`, so:

- `aws sso login` succeeds
- `aws sts get-caller-identity` returns a valid identity
- the cluster returns **`Unauthorized`**

Presents as a permissions bug; is a wrong-profile problem. Hence a dedicated `op-qa` profile, and it's called
out first in the message to Idris.

⚠️ **Do not "fix" this by mapping `AWSAdministratorAccess` in `aws-auth`** — that would silently grant
cluster-admin to everyone with account admin. A dedicated permission set is what makes "who has cluster
access" an answerable question. Same reason cloud prod maps `v-prod`, not the admin role.

## 5. `livenessProbe` + `hostNetwork` + loopback-only listener = CrashLoop

The authenticator binds **127.0.0.1 only**. An `httpGet` probe without `host:` is sent by kubelet to the
**node IP**, which nothing is listening on. All three pods CrashLooped **~140 times over 8 hours**,
presenting as intermittent `dial tcp [::1]:21362: connect: connection refused` in the apiserver log and
sporadic `Unauthorized` for users.

Fix: `tcpSocket` with an explicit `host: 127.0.0.1`. (`tcpSocket` rather than `httpGet` because `/healthz`
is unverified on this build.)

**The misdiagnosis is worth recording too:** the `[::1]` in the error read as an IPv4/IPv6 mismatch, and the
"fix" attempted was `--address=::1`. That edit never applied (unset `$EDITOR`), and the thing that actually
helped was the pod restart triggered by `kubectl apply`. Restarts that coincide with a fix are not evidence
of the fix.

## 6. `kubectl apply` merges probe handlers — use `replace`

Applying the corrected `tcpSocket` probe over a live object still holding `httpGet` yields:

```
livenessProbe.tcpSocket: Forbidden: may not specify more than 1 handler type
```

Strategic merge adds the new handler beside the old one. The file was correct; the update method wasn't.
Use `kubectl replace`, or let Flux (server-side apply) own it.

## 7. Post-apply Flux bootstrap step is broken on QA

```
bash -c rm -rf /tmp/iaac-talos-flux-cluster && git clone ...
rm: missing operand
```

An Octopus variable renders empty, so `rm -rf` gets no operand and the step exits 1 — failing the deploy
*after* a successful terraform apply. Harmless today (Flux is already bootstrapped on QA) but it has never
worked here, and **it will break rebuild-to-validate**, which is the whole point of INFRA-1589. Separate
ticket.

## What to carry to dev and prod

- Permission set per cluster: `op-dev-platform-admin`, `op-prod-platform-admin`. Near-empty inline policy
  (`sts:GetCallerIdentity`) — the K8s grant comes from *which role was assumed*, not from IAM permissions.
- `TF_VAR_enable_aws_iam_authenticator` **and** `TfApply` must both be set as Octopus variables, scoped to
  the environment, and the release re-snapshotted.
- Order is not optional: DaemonSet writes the webhook kubeconfig on **every** control-plane node **before**
  the apiserver flag lands, or that node's apiserver will not start.
- Prod should **not** get a standing admin assignment. Reader by default; admin via a separate permission
  set with a short session duration.
