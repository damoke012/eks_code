## 3. Tim's question is the real one, and it got no answer

> *"when you deploy a new image… how is it gonna affect that data? Let's say we add a column,
> remove a column, or change a column's data type… think of an ALTER command."*

He is asking about **schema evolution**, and he is right to. The current answer, stated plainly:

* `apply.sh` tracks each file by hash. Unchanged file → skipped. New file → applied.
* **A file that CHANGED after being applied is REFUSED, not re-run.** Deliberate: RisingWave has
  no read-write transactions, so a half-applied edit cannot be rolled back, and editing a
  `CREATE SOURCE` means dropping and recreating a streaming job that then re-reads the topic.
* So today the answer to "how do I add a column" is: **add a new numbered file.** There is no
  ALTER path and no down-migration.

That is a real limitation, not a finished design. Flyway was evaluated and rejected (its
bookkeeping needs transactions and types RW rejects — INFRA-1491). **Owning this question is
the difference between a RisingWave script runner and a platform pattern.**

## 4. The reframe: this is app onboarding, RisingWave is app #1

Doke, on the second call: *"we are doing it for RisingWave, but we want this to be for the
platform as a whole."* That is the right instinct and it has not been made real. Everything so
far is named `etl-pipeline`, `risingwave-etl`, `app-risingwave`.

**What makes it a pattern rather than a one-off** — five contracts an app owner has to satisfy,
and nothing else:

| # | Contract | RisingWave's instance |
|---|---|---|
| 1 | A repo with a `build/Dockerfile` producing one artefact | `risingwave-pipeline` |
| 2 | `deploy/base` + `deploy/overlays/{qa,prod}`, image pinned by **digest** | done |
| 3 | Nothing environment-specific in the image; config via ConfigMap, credentials via ExternalSecret | done 2026-08-27 |
| 4 | Secrets Manager paths at `op-usxpress-<env>/<app>/<connector>` | `…/risingwave/{root,postgres,kafka,mongodb}` |
| 5 | An Argo CD Application generated by the platform ApplicationSet | `risingwave-etl` |

Anything an app team must do that is not on that list is a platform gap, not their problem.

**The deliverable that makes it real:** promote `app-template/` to a documented, versioned
scaffold with the five contracts written as acceptance criteria, and onboard a second,
non-RisingWave app against it. One app is an example; two is a pattern.
