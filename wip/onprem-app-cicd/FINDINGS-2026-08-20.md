# 2026-08-20 — the on-prem app delivery path works end to end, and what it cost to find out

**Scope:** `op-usxpress-qa` only. Prod has the platform half but no Git credential and no
ApplicationSet. Dev is untouched.

INFRA-1647 (Argo CD Git credential) and INFRA-1648 (smoke test) are **done**. Six defects
were found, all by running the thing rather than by reading it, and every one of them
reported green until something actually used the value.

## The proof

```
 path                      | sha          | applied_at                   | applied_by
 smoke/001-connectivity.rw | 4b65ef49e1c4 | 2026-08-20 16:26:47.88722+00 | argocd-qa
```

One row in `pipeline_applied` on QA's Postgres. To write it, every link had to hold:
GitHub Actions built the image and pushed it **by digest** · ECR served it cross-account ·
`ecr-pull-secret` authenticated the pull · Argo CD read an **internal** repo over a deploy
key · the QA overlay rendered · the sync-hook Job ran **inside** the cluster · External
Secrets supplied the credentials · Postgres accepted them · RisingWave executed the SQL.

That is the first time an application has been delivered to an on-prem cluster this way.

## The six defects, in the order they surfaced

| # | Defect | What it looked like | What it was |
|---|---|---|---|
| 1 | Argo CD held **no Git credential at all** on QA or prod | `ComparisonError: authentication required` | no secret carried `argocd.argoproj.io/secret-type`; masked for a day because the Application also pointed at a missing path on a branch that does not exist |
| 2 | `risingwave/etl-pipeline` had **no ECR repository policy** | kubelet `403 Forbidden` on the manifest HEAD — reads like a broken pull secret | ECR authorises **per repository**. The pull secret authenticates to the *registry*; a repo with no policy is unreadable from any other account. Push was unaffected — the GHA role is in the registry's own account, so IAM alone covers it |
| 3 | QA overlay carried a **dev service name** | `could not translate host name "postgres-postgresql…"` | QA runs `pg-postgresql`. Fourth instance of a scaffolded file inheriting the source environment's identifiers |
| 4 | `PG_USER` asserted in a ConfigMap, password in Secrets Manager | `password authentication failed for user "postgres"` | SM held username `risingwave`. The password was paired with an account that does not exist, and the error named the wrong cause |
| 5 | **QA Postgres never learned its own rotated password** | `password authentication failed for user "risingwave"` with four consumers holding identical values | `initdb` ran 2026-08-11 19:20 UTC; the secret was rotated 2026-08-12 13:35 UTC. `POSTGRES_PASSWORD` only applies at initialisation |
| 6 | The hook Job **deleted its own failure evidence** | "No resources found" every time we looked | `hook-delete-policy: BeforeHookCreation` plus Argo CD's 5 automatic retries: each retry destroyed the previous attempt's pod and logs |

## Defect 5 is not ours, and it is the serious one

Four things agreed with each other and none of them agreed with the database:
Secrets Manager, `pg-credentials`, `risingwave-pg-credentials`, and our Job — all
`d73aa714…`. The database still held the 2026-08-11 value.

**Why nobody noticed for 8 days:** `risingwave-meta-default-0` was created 2026-08-11 17:15,
*before* the rotation, so its env was resolved from the pre-rotation secret. Env from
`secretKeyRef` is resolved at **pod** creation, not container restart — so its 238 container
restarts (all in the first 16 hours, exit 139 / SIGSEGV) each replayed the old password and
each succeeded. The fault was invisible precisely because the pod never got recreated.

The first thing ever to use that credential fresh was today's smoke test.

**Fixed** by `ALTER USER risingwave WITH PASSWORD` from inside `pg-postgresql-0` — `initdb`
enabled `trust` for local connections, so the change needs no prior password.

⚠️ **Left inconsistent:** the fix inverted meta's exposure. Its pod env still holds the
pre-rotation password, so a **container** restart now fails where a **pod** recreation
succeeds. Recreating `risingwave-meta-default-0` closes it. Not done at time of writing.

⚠️ **Check dev and prod for the same shape.** Any Postgres built before its secret was
rotated has this fault, dormant until something recreates the pod.

## Proven

* The full delivery path, QA, 2026-08-20 — evidenced by the `pipeline_applied` row above.
* A **repository deploy key** authenticates Argo CD to an internal repo: repo-owned, no
  expiry, unaffected by offboarding, needs repo admin rather than org ownership.
* ECR cross-account pull requires a **per-repository policy**; the pull secret is not enough.
* `initdb` on QA ran 2026-08-11 19:20 UTC; SM `LastChanged` 2026-08-12 13:35 UTC.
* `dare-x` is a **member** of `variant-inc`, not an owner — org GitHub Apps need someone else.
* **No Terraform manages ECR anywhere in the org.** `aws_ecr_repository` appears once, in an
  interview sandbox. `iac-tf-common-endpoints` has plan/apply workflows but assumes
  `github-iac-ecr-vpc-endpoint-role`, which **does not exist** in 064859874041 — that repo is
  dormant. The GitHub OIDC provider does exist there.

## Tested and killed

* **A fine-grained PAT for Argo CD** — rejected on the requirement "no CI/CD tied to a
  person". A fine-grained PAT is owned by a **user account even when the resource owner is
  the org**; only a shared machine account like `usx-devops` avoids that, and it was not
  reachable. The deploy key meets the requirement today.
* **`iac-tf-manual-runs` as the Terraform home** — it commits `terraform.tfstate` to git and
  has no apply workflow. Laptop applies with state in the repository is the opposite of
  what was asked for.
* **`hook-delete-policy: HookSucceeded` alone** — fixes the failure case and breaks the
  success case: it deletes the evidence *of success*, and a retained failed Job then blocks
  the next sync with `AlreadyExists`. Correct setting is
  `BeforeHookCreation,HookSucceeded` **plus** a lower ApplicationSet retry limit, so a
  failure stops at once and persists until someone deliberately re-syncs. ~~**Not yet
  applied.**~~ Applied and verified 2026-08-20 19:30Z — `risingwave-pipeline#15` for the
  hook policy, `iaac-talos-flux-platform#100` for `retry.limit: 1`, confirmed live on the
  ApplicationSet as `{"backoff":{"duration":"30s","maxDuration":"2m"},"limit":1}`. The same
  PR flipped `require-approved-registry` and `require-image-digest` to `Enforce`.

## Traps

1. **ECR authorises per repository.** A new repository is unreadable cross-account until it
   has a policy. The symptom points at the pull secret, which is fine. Onboarding is now six
   changes, not five — `ONPREM-CICD.md` §4.2.
2. **Do not model new repository policies on `lazy/api`.** It grants `PutImage`,
   `InitiateLayerUpload` and `CompleteLayerUpload` to every principal in org `o-yza5l1xhrc`
   (INFRA-1643). Ours grants three read actions to three named accounts.
3. **`POSTGRES_PASSWORD` applies only at `initdb`.** Rotating the secret afterwards updates
   every consumer and never the database. Nothing reports this.
4. **Env from `secretKeyRef` resolves at pod creation.** A container restart replays the old
   value; only pod recreation picks up a rotation. A workload can run for months on a
   credential that no longer exists anywhere else.
5. **`Synced Healthy` is not a statement about the workload.** Argo CD reported it while the
   Job was in `ImagePullBackOff`. Third member of the family after `SecretSynced` and the
   Flux `Ready=True` on a two-day-dead token.
6. **A username and a password that live in one secret must travel together.** Split across
   a ConfigMap and Secrets Manager, they drift, and the error names the wrong cause.
7. **`gh pr merge` requires the PR number when `--repo` is given** — otherwise it errors and
   everything after it in the block runs against the unmerged state.
